# 工作量评估自动化实现方案

> 目标：输入**需求文档**（docx），自动输出以 `副本造价评估-…（软件开发功能点评估）` 为模板的**成品工作量评估表**（xlsx）。
> 本方案先完成分析评估，形成可落地、可复核、可验证的实现路径。

---

## 一、背景与目标

公司造价评估采用 **IFPUG 国际标准功能点估算法**。现有两套 Excel：

| 文件 | 定位 |
|---|---|
| `1.IFPUG国际标准功能点估算法计算 -票据标识功能升级项目.xlsx` | **识数源**：从需求说明书逐条识别功能点、判定复杂度、累计未调整功能点 |
| `副本造价评估-天津银行_…（软件开发功能点评估）.xlsx` | **成品模板**：按「功能点 → 规模 → 工作量 → 费用」输出最终造价表 |

**业务诉求**：评估人员无需手工在 Excel 里逐行填写，只要提供需求说明书，系统自动完成「识别 → 计数 → 套模板 → 生成成品表」。

## 二、现状方法解读

### 2.1 IFPUG 五大功能类型

| 类型 | 全称 | 含义 | 权重（低/中/高） |
|---|---|---|---|
| ILF | 内部逻辑文件 | 内部维护的数据 | 7 / 10 / 15 |
| EIF | 外部接口文件 | 引用外部系统数据 | 5 / 7 / 10 |
| EI | 外部输入 | 新增/修改/删除类处理 | 3 / 4 / 6 |
| EO | 外部输出 | 派生数据的输出（含报表/报文） | 4 / 5 / 7 |
| EQ | 外部查询 | 仅查询无派生数据 | 3 / 4 / 6 |

系数表固化在源文件 `公式应用数据表`。

### 2.2 复杂度判定矩阵（规则引擎核心）

复杂度=功能类型 + 两组计数维度，按矩阵查表：

- **ILF/EIF**：`记录元素 RET × 数据元素 DET`
  - DET 档位：`[1,19] / [20,50] / ≥51`
  - RET 档位：`1 / [2,5] / ≥6`
- **EI**：`文件引用数 FTR × DET`
  - DET 档位：`[1,4] / [5,15] / ≥16`；FTR 档位：`[0,1] / 2 / >2`
- **EO/EQ**：`FTR × DET`
  - DET 档位：`[1,5] / [6,19] / ≥20`；FTR 档位：`[0,1] / [2,3] / ≥4`

每个功能类型一张 3×3 矩阵（低/中/高），随后映射到 2.1 表的权重 → 未调整功能点 **UFP**。

> 注：源文件表头将 `FTR` 误写为 `FRT`，实现时统一按标准 IFPUG `FTR`（引用文件类型数）处理。

### 2.3 功能点调整（`功能点估算法-计算表`）

1. `UFP = Σ(各类型按复杂度加权累加)`
2. `TDI = Σ` 14 个系统特征因子的影响程度分（0~5）
3. `VAF = TDI × 0.01 + 0.65`（调整系数）
4. `调整后功能点 = UFP × VAF`

### 2.4 成品模板计算链路（`副本造价评估`）

规模估算 Sheet 明细行（核心录入区）：

```
US = UFP × 重用程度系数 × 修改类型系数
```

费用估算 Sheet（自动计算区）：

```
调整后规模(FP) = 规模估算结果 × 规模变更调整因子(按估算时机)
  规模变更调整因子：早期1.39 / 中期1.21 / 晚期1.10 / 交付后1.00

未调整工作量(人天) = 调整后规模 × 基准生产率(人时/FP) ÷ 8
  基准生产率三档：下限8.54 / 中值10.67 / 上限12.80（生产系统10.67为模板中值）

调整因子链条 = 应用类型 × 质量特性 × 完整性级别 × 开发语言 × 开发团队背景
调整后项目工作量(人天) = 未调整工作量 × 调整因子

外包工作量 = 调整后项目工作量 − 自主开发工作量
项目费用(万元) = 工作量(人天) ÷ 22 × 人月基准单价(2.57万)
```

**链路校验**（用模板示例数据倒推，全部吻合）：
`调整后规模127.13 → ×8.54÷8=135.65 人天 → ×0.80=108.52 人天 → ÷22×2.57=12.68 万元`。

### 2.5 各系统参数库（从模板「模板使用说明&基础参数」提取，全部需固化）

| 参数族 | 内容 |
|---|---|
| 重用程度系数 | 高0.33 / 中0.67 / 低1.00 |
| 修改类型系数 | 新增1.00 / 修改0.80 / 删除0.20 |
| 应用类型系数 | 业务处理1.0 / 应用集成1.2 / 科技1.2 / 多媒体1.3 / 智能信息1.7 / 系统软件1.7 / 通信控制1.9 / 流程控制2.0 |
| 质量特性（±1） | 分布式处理 / 性能 / 可靠性 / 多重站点，各自 0 状态3档 |
| 开发语言系数 | C1.5 / Java、C++、C#1.0 / PB、ASP0.6 |
| 开发团队背景系数 | 同类行业0.8 / 相关1.0 / 无背景1.2 |
| 完整性级别系数 | C/D1.0 / A/B1.1 / A(全流程)1.3 |
| 系统类别生产率 | 生产系统10.67 / 管理类6.83 / ESB4.08 / 大数据平台5.55 |

## 三、总体架构

```
┌────────────┐   ①    ┌──────────────┐   ②    ┌──────────────┐   ③    ┌────────────┐
│ 需求说明书 │ ───► │  需求解析与   │ ───► │  IFPUG 规则   │ ───► │ 成品表生成  │
│  (docx)    │       │ 功能点识别    │       │  引擎(计数)   │       │ (套模板xlsx)│
└────────────┘       └──────────────┘       └──────────────┘       └────────────┘
        ▲                  │  (LLM识别)             │                 │
        │                  ▼                       ▼                 ▼
        │         ┌ ─ 候选功能点清单 ─ ┐      UFP + 复杂度      按文件2四个Sheet
        │         │  类别/RET/DET/FTR  │      类别/重用/修改      自动填充与公式
        │         └ ——— 人工智能审 ——─┘                        └──────┬──────┘
        │                ▲ 人工核对JSON                               │调整因子/参数
        └──────────── ②'  修正后进入计数 ──────────────────────────► 参数库(config)
```

**三类输入能力**：
1. **读入**：解析 docx 需求说明书 → 结构化功能描述
2. **识别**：LLM 按 IFPUG 五类判定，输出候选功能点（类别、复杂度维度 RET/DET/FTR、功能项描述）
3. **生成**：规则引擎计数 + 套用模板保真生成成品 xlsx

## 四、自动化程度选择（关键决策）

| 路线 | 工作方式 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A. 半自动（推荐）** | AI 识别生成候选清单 → 人工确认复核 → 脚本自动套模板出表 | 可复核、可追溯、可纠错，符合造价审计要求 | 需一次人工确认 | ✔ 首选 |
| B. 全自动 | AI 直接生成成品 xlsx | 省人工 | 出错难发现、审计不可靠、审价不采用 | ✖ 仅作辅助原型 |

> 造价/报价属于对外审计类场景，**必须可复核**。推荐 A：**AI 出候选 + 人工确认 + 自动套表**。人工只需确认功能点清单，不做 Excel 手工工作。

## 五、模块设计

### 模块 1：需求解析器
- 输入：`docx`
- 用 `python-docx` 抽取标题层级、正文、表格、清单项
- 输出：结构化需求片段（可导航引用，供 LLM 与人工定位）

### 模块 2：功能点识别（LLM）
- 按 IFPUG 规则，将每个需求片段映射为一条或多条功能点：
  - **EI**：录入/修改/删除/导入/报文发送类处理
  - **EQ**：纯查询/下载模板/定时统计展示
  - **EO**：派生报表、加工口径、数据报送
  - **ILF**：新增/修改的数据表、字段
  - **EIF**：引用外部系统数据
- 同时预估计数维度：`RET / DET / FTR`（或直接给复杂度档位），及 `重用程度`、`修改类型`
- 输出 JSON：`[{序号, 涉及系统, 一层模块…四级模块, 功能项描述, 功能点计数项名称, 类别, RET/DET/FTR, 重用, 修改类型, 备注}]`

### 模块 3：IFPUG 规则引擎
- 内置 2.2 的复杂度矩阵与 2.1/2.4 的系数表（纯代码、可单测）
- 输入修正后的功能点清单 → 输出 `UFP`、`US`、调整后功能点、工作量、费用（与 Excel 公式结果一致）

### 模块 4：成品表生成器（套模板）
- **以文件2为母版，openpyxl 打开副本**，仅改写需填写的白色区域：
  - `项目特征`：按项目情况填计数时机、应用类型、质量特性、语言、团队背景
  - `规模估算`：逐行写入明细（A5:N），US 列写公式 `=J列×K列×L列`
  - `费用估算`：保留原公式自动计算结果，`涉及系统`按清单自动展开多系统列
- 其余固定公式与样式**原样保留**，保证与人工 Excel 完全一致

### 模块 5：参数库
- `config.xlsx` 或 `config.py`：固化 2.5 全表参数与 14 个系统特征因子库，声明式可改

### 模块 6：人工审核清单
- 生成可读 `checklist.json` / 表格：逐条展示候选功能点、判定依据、可修订字段
- 人工确认（或修订）后重新跑 3 → 4，避免在 Excel 上返工

## 六、技术选型

| 项 | 选型 | 说明 |
|---|---|---|
| 语言 | Python 3.10+ | 生态成熟 |
| 读 docx | python-docx | 解析需求说明书 |
| 写 xlsx | openpyxl | 复制母版保真、写公式 |
| 规则引擎 | 纯 Python + pytest | 复杂度矩阵/系数表可单测，正本清源 |
| AI 识别 | LLM（TraeCode 主对话/脚本） | 功能点候选与判定依据生成 |
| 工程结构 | 单包 + config 声明参数 + 命令行入口 | 简约、可复用 |

## 七、实施步骤

1. **抽取参数库**：把文件2「模板使用说明&基础参数」全部转成 config（已完成分析，见 2.5）
2. **实现规则引擎**：复杂度矩阵 + 权重 + VAF + 工作量/费用链路，用示例数据做单测校准
3. **实现模板生成器**：openpyxl 打开母版副本，验证「写明细 → 公式自算 → 结果与文件2示例一致（UFP=234 / US=105.07）」
4. **实现需求解析器**：解析 docx 需求说明书为结构化片段
5. **接 LLM 识别**：生成候选功能点 JSON + 判定依据
6. **人工审核清单**：输出 checklist，修订后回灌引擎
7. **端到端验证**：用示例需求说明书跑完整链路，对照源 Excel 结果核定偏差
8. **封装命令行**：`python estimate.py --req 需求.docx --out 成品.xlsx`

## 八、验证方案

- **规则引擎单测**：用源文件 `公式应用数据表` 边界值（RET/DET/FTR 档位临界点）逐项断言复杂度
- **链路校准**：以文件2示例（多功能点、多系统、多类别）为金标准，要求引擎结果与模板公式输出偏差 < 0.1%
- **识别质量**：以文件1已批复的功能点清单为基准集，评估 LLM 识别对各类别的查全/查准，≥80% 后进入人工确认流程

## 九、风险与对策

| 风险 | 对策 |
|---|---|
| LLM 误判类别/维度 | 强制人工审核环节，输出判定依据便于抽查；建议按系统/模块分批复核 |
| 需求文档结构不规范 | 解析器做章节/表格/列表容错；无法定位的内容转入「待人工确认」 |
| 模板版本更替 | 母版与参数库独立管理，参数库声明式，改参数不改代码 |
| 复杂度维度主观性 | DET/RET/FTR 提供计数提示与抽检规则，必要时沿用文件1逐条计数的严谨度 |
