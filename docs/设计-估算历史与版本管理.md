## 2. 数据模型

新建 `data/estimation.db`（与 `pert.db` 平级、独立职责；复用 `server` 侧既有 SQLite 连接封装风格）：

```sql
CREATE TABLE IF NOT EXISTS estimation_history (
  id            TEXT PRIMARY KEY,            -- uuid
  created_at    TEXT NOT NULL,               -- ISO8601 本地时间
  updated_at    TEXT NOT NULL,
  title         TEXT NOT NULL,               -- 需求标题（生成 sid 时的基名）
  source_name   TEXT,                        -- 上传文档原始文件名（可空：粘贴文本场景）
  method        TEXT NOT NULL,               -- 估算功能点 | 预估功能点 | NESMA预估 | NESMA估算
  params_json   TEXT NOT NULL,               -- 识别参数快照：{llmEnabled, feeVersion, ctxDir, ...}
  items_json    TEXT NOT NULL,               -- 复核确认后的功能点明细（与 /api/generate 请求体一致）
  summary_json  TEXT,                        -- 服务端返回的 summary（US 合计等）
  sid           TEXT,                        -- 成品文件名（data/generated/<sid>）
  version_group TEXT NOT NULL,               -- 版本组：同标题首次生成为 uuid，重开/另存沿用
  version_no    INTEGER NOT NULL DEFAULT 1,  -- 组内递增：1,2,3…
  schema_ver    INTEGER NOT NULL DEFAULT 1   -- items_json 结构版本，便于迁移
);
CREATE INDEX idx_hist_created ON estimation_history(created_at DESC);
CREATE INDEX idx_hist_vgroup  ON estimation_history(version_group, version_no);
```

**要点**
1. `items_json` 与 `/api/generate` 的请求体字段一致（system/m1~m4/desc/count_item/type/reuse/modify），重开时可直接还原为复核态，**不做字段翻译**。
2. `version_group` 语义：重开（不换标题）→ 沿用原组、version_no+1；**另存为（换标题）→ 新建组**。这使"同口径多次估算"天然聚成一组，是 FR-2.5 Diff 的键。
3. 保留策略：默认保留最近 **500** 条（`WE_HIST_MAX` 可配），写入时惰性清理最旧；删除接口支持手动清理。
4. 敏感性：明细可能含客户业务信息，库文件不脱敏但**不参与任何上传**；诊断包导出时排除该库（FR-ENG04 约束）。

## 3. API 设计（全部挂 `/api` 前缀，沿用现有 hand-rolled router 风格）

| 方法 | 路径 | 说明 | 返回 |
|---|---|---|---|
| GET | `/api/history?query=&limit=50&offset=0` | 列表（时间倒序），query 对 title/source_name 做 LIKE | `{ok, total, rows:[{id,created_at,title,method,count,us_total,sid,version_group,version_no}]}` |
| GET | `/api/history/{id}` | 详情（含 items_json 解析后的明细数组） | `{ok, row, items:[...]}` |
| DELETE | `/api/history/{id}` | 删除单条（不删成品文件） | `{ok}` |
| GET | `/api/history/{id}/group` | 同组各版本列表（重开时提示"这是第 N 版"） | `{ok, versions:[...]}` |
| — | `/api/generate` 成功响应前 | **落库接线点**：服务端在返回响应前写入一条历史（见 §4） | 无新端点 |

**落库接线点（关键设计）**：写在 `do_POST /api/generate` 的成功分支内、`_gen_progress_set(job,100,...)` 之后：把本次 `items`、`method`、`title`、`sid`、`summary`、`recalc_mode` 组装落库。若前端传 `reopen_group`（重开场景），沿用该 version_group 并自增 version_no。**落库失败只记日志、不影响生成响应**（try/except 包裹，与既有 `_gen_progress_set` 容错风格一致）。

**请求扩展**：`/api/generate` 请求体新增可选字段 `reopen_group`（重开时的 version_group）与 `fee_version`（费率口径，FE-03 预留）；两者均向后兼容（缺省不传行为不变）。

## 4. 前端设计（frontend/index.html）

1. **入口**：IFPUG 工作页步骤条外、右上角新增「历史估算」按钮（iconbtn 规范：`history` 图标 + title/aria）。点击打开历史面板（复用玻璃卡容器，不做新 page，避免路由复杂化）。
2. **历史面板**：搜索框 + 列表（时间/标题/功能点数/US 合计/版本号徽标）+ 操作列（详情 / 重开 / 删除）。分页：每页 50，滚动加载。
3. **重开流程**：
   ```
   点「重开」 → GET /api/history/{id} → 确认弹层（显示该版本功能点数与生成时间）
   → goPage('work') → 全局 items=历史明细；curFile 元信息置为历史记录（title=历史标题）
   → goStep('review') → 用户修改 → 「确认无误·生成结果」→ /api/generate 带 reopen_group=<原组>
   → 新版本落库（version_no+1），成品文件名 = <标题>-工作量评估.xlsx（同名覆盖语义与现状一致）
   ```
4. **另存为**：历史详情「另存为」= 重开后在复核页改标题（curFile 基名），生成时**不传** reopen_group → 新版本组。
5. **会话恢复（FR-1.8）**：生成成功落库后，把 `last_history_id` 写 localStorage；页面 `DOMContentLoaded` 时若存在该键且 `items` 全局为空 → 顶部提示条「检测到上次估算（标题/时间），是否恢复？」→「恢复」走重开流程、「忽略」清键。
6. **UI 细节**：列表行内版本徽标（v2/v3）；重开后的复核页顶部显示「正在修订：第 N 版（基于 <时间>）」；全部新文案走现有 `#toast` 与引导体系。

## 5. Diff 数据基础（FR-2.5，本期仅数据层）

- `version_group + version_no` 已可定位任意相邻版本；`items_json` 每条明细带稳定 `seq`。
- 阶段二实现 Diff 时：`GET /api/history/{id}/diff?against={id}` 按 (system+desc) 归一化键对齐，输出 added/removed/changed（type/reuse/modify 变更）三类；本期**只保证落库字段完整**，不改接口。
